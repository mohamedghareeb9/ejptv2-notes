# 3.2 CMS and WordPress Security Testing

Content management systems (CMSs) provide an application framework for publishing and managing website content. A CMS assessment combines ordinary web reconnaissance with identification of the CMS core, themes, plugins/modules, user accounts, and exposed files.

INE's March 2026 eJPT update specifically calls out CMS security fundamentals and WordPress security testing and exploitation. This chapter provides a foundation for those tasks; it is not a substitute for the current INE learning-path labs.

## 1. CMS identification

Start with ordinary web reconnaissance and verify the application before selecting CMS-specific tools.

Useful indicators may include:

- Page source, generator metadata, response headers, and distinctive asset paths.
- Common WordPress paths such as `/wp-content/`, `/wp-includes/`, `/wp-admin/`, and `/wp-login.php`.
- A WordPress REST API endpoint such as `/wp-json/`, if enabled and exposed.
- Login pages, theme assets, plugin assets, and error messages.

These indicators are clues, not proof. Paths can be renamed or blocked, and reverse proxies or caching layers can affect what a scanner sees.

## 2. WordPress components to recognize

| Component | What it is | What to review |
|---|---|---|
| WordPress core | Main application files and built-in functionality | Version, support status, and security updates |
| Themes | Control presentation and may contain executable code | Active theme, version, maintenance status, and known vulnerabilities |
| Plugins | Add application features and often expand the attack surface | Installed plugins, versions, update status, and known vulnerabilities |
| Users and roles | Identities and permissions within the site | Publicly exposed usernames and whether roles follow least privilege |
| Configuration | Settings for the application and database | Accidental exposure of configuration backups or secrets |
| Content and uploads | User-provided pages, media, and files | Unexpected executable files, exposed backups, and unsafe permissions |

WordPress commonly stores themes and plugins under `wp-content`. The exact filesystem layout may differ if the installation has been customized.

## 3. WPScan enumeration

[WPScan](https://github.com/wpscanteam/wpscan) is a WordPress security scanner. Its documentation describes enumeration modes for identifying versions, plugins, themes, usernames, and other exposed resources.

Basic scan (WPScan 4.x):

~~~bash
wpscan --url https://<TARGET>/
~~~

WPScan 4.0 changed the default scan behavior to a more explicit, minimal scan. To enumerate vulnerable plugins, vulnerable themes, and user IDs, request those checks explicitly:

~~~bash
wpscan --url https://<TARGET>/ --enumerate vp,vt,u
~~~

If you need to enumerate all plugins rather than only those with known vulnerabilities, use `ap`:

~~~bash
wpscan --url https://<TARGET>/ --enumerate ap --plugins-detection passive
~~~

WPScan supports passive, mixed, and aggressive detection modes. Passive detection can reduce the number of requests, but may miss components that are not exposed through passive fingerprints. Select a mode that matches the engagement's request limits and required coverage.

The available enumeration options include:

| Option | Meaning |
|---|---|
| `vp` | Vulnerable plugins |
| `ap` | All plugins |
| `p` | Popular plugins |
| `vt` | Vulnerable themes |
| `at` | All themes |
| `t` | Popular themes |
| `u` | User ID range / user enumeration |

WPScan 4.x has additional enumeration choices, including backup folders (`bf`), configuration backups (`cb`), and database exports (`dbe`). Check the installed version's `wpscan --help` and the current user documentation for its exact options and defaults. Enumeration can generate many HTTP requests; use it only within scope and choose a request intensity appropriate to the engagement.

**Licensing note:** WPScan's own documentation states that its scanner is licensed under a custom license and that commercial use may require a paid license. Check the current license terms before using it in paid client work.

## 4. Interpreting findings

A scanner result is a lead to validate, not a confirmed vulnerability.

For each identified core, theme, or plugin version:

1. Record the exact component name and detected version.
2. Confirm the version using a second source when possible.
3. Check the vendor's release notes and a credible vulnerability reference such as [NVD](https://nvd.nist.gov/) or the relevant CVE record.
4. Confirm that the affected version range and vulnerable feature match the target.
5. Consider configuration, authentication requirements, and compensating controls.
6. Report the evidence and impact without claiming exploitability based only on a version banner.

Avoid running exploit code merely because a scanner reports an outdated component. Review the exploit's behavior and validate only with explicit authorization.

## 5. Common WordPress security issues

The official WordPress hardening guidance highlights several areas that are useful to assess:

- **Outdated core, themes, or plugins:** unsupported or unpatched components may contain known vulnerabilities.
- **Untrusted extensions:** themes and plugins should come from trusted sources and be maintained.
- **Weak authentication:** weak or reused passwords can expose administrative accounts. Test login controls only within the agreed scope and with an approved rate limit.
- **Exposed files:** check for accidentally published backups, database exports, and configuration copies.
- **File permissions:** excessive write access can allow an application compromise to become a broader server compromise.
- **Database privileges:** the application database account should not receive unnecessary administrative privileges.
- **Administrative file editing:** access to edit theme or plugin code through the dashboard increases the impact of an administrator-account compromise.
- **Insufficient backups and logging:** backups support recovery; logs support investigation and verification.

The WordPress security guidance recommends keeping the core and installed extensions updated, using trusted themes/plugins, restricting permissions, planning backups, and monitoring the site.

## 6. Additional CMS recognition: Drupal

The original study cheat sheet also includes Drupal reconnaissance topics. For an authorized assessment, recognize the following as possible enumeration areas:

- Drupal version and exposed version information.
- Publicly discoverable usernames.
- Installed modules and their versions.
- Hidden or exposed pages and files.
- Configuration files or database details accidentally exposed through the web server.

As with WordPress, confirm the exact product/version and affected conditions before treating a finding as a vulnerability.

## 7. Safe assessment workflow

1. Confirm the domain, application, and permitted testing scope.
2. Perform ordinary web reconnaissance and identify likely CMS indicators.
3. Confirm the CMS and collect version evidence.
4. Enumerate themes, plugins/modules, and publicly exposed user information using an appropriate request intensity.
5. Correlate component versions with vendor advisories and vulnerability references.
6. Validate only the findings and impacts permitted by the rules of engagement.
7. Preserve logs and evidence; do not alter or delete them to conceal test activity.
8. Report the component, evidence, impact, and recommended remediation.
